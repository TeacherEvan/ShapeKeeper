7. Tagging & Releases

Single tag in history: V1.0. There is no semver sequence (v2.0.0, v4.3.0, etc.). The README references version 4.3.0 but there is no corresponding Git tag.

The project appears to use version strings in config.js or README.md rather than Git tags for release tracking. This is acceptable for a static-site deployment model (Vercel), but if you ever want git describe to work for debugging production builds, establish a tag convention:

  • Option A (lightweight): Tag the production deploy commits. E.g. git tag v4.3.0 <deploy-commit> && git push origin v4.3.0. No need to tag every commit — just the ones that ship to production.
  • Option B (conventional): Use v<major>.<minor>.<patch> for every release and rely on GitHub Releases as the changelog. This gives you git describe --tags for free.
  • Option C (do nothing): Keep the current model where version is tracked in config.js. This is fine for Vercel deployments but loses the ability to git checkout v4.3.0 to inspect a shipped build.

9. Missing Git Mechanisms

9a. .gitattributes — recommended addition

Without .gitattributes, Git uses platform defaults for line endings and has no binary-detection rules. For a multi-OS project, add this file at the repo root:

# Line endings: normalize to LF on checkout
* text=auto eol=lf

# Binary files — do not normalize
*.png binary
*.jpg binary
*.jpeg binary
*.gif binary
*.webp binary
*.ico binary
*.svg text eol=lf

# Generated / lock files — LF only
package-lock.json text eol=lf
yarn.lock text eol=lf

# Convex TypeScript — LF only
convex/**/*.ts text eol=lf
convex/**/*.js text eol=lf

This prevents the classic "one contributor on Windows checks in CRLF, everyone else sees a diff of every line" problem. It also prevents Git from storing duplicate blobs for the same file in two line-ending forms.

9b. Pre-commit hooks — currently absent

There is no .git/hooks/ enforcement visible. This repo relies on CI (ESLint + vitest) rather than pre-commit hooks. That's a valid choice for a small team, but consider:

  • Husky or a simple pre-commit script that runs npx eslint --fix on staged .js files before commit. This catches lint drift at commit time rather than at CI time.
  • pre-commit (the Python-based framework) is another option — it can run eslint, prettier --check, and npm run verify as pre-commit steps without committing to a specific JS toolchain.

This is a NICE-TO-HAVE, not a defect. The current CI-gated approach works.

9c. No signed commits

None of the commits are GPG-signed. For a personal/small-team project this is fine. If the project ever becomes security-sensitive or multi-organizational, enable commit signing via commit.gpgsign = true in Git config and add verified badges on GitHub.

11. Summary of Findings by Severity

  • HIGH 20 merged branches still on the remote. Every one of the 20 branches listed in §3a is fully merged into main and should be deleted. This is the single biggest hygiene issue in the repo.   • HIGH Author identity fragmentation. 8 distinct author strings, at least 4 referring to the same human. This makes git shortlog, git blame annotations, and any contributor statistics unreliable. Fix: re-set user.name / user.email consistently on the committing machine, and optionally use git filter-repo or git rebase to coalesce historical identities if a clean record is wanted.
  • MEDIUM No .gitattributes. For a multi-OS project, this invites line-ending drift. Adding a .gitattributes file is a 5-minute one-time action with long-term payoff.
  • MEDIUM No release tags for current version. The project is at 4.3.0 but the only tag is V1.0. If you ever need to checkout a shipped build for debugging, you can't. Adding a tag on the production deploy commit is low-cost and high-value.
  • MEDIUM package-lock.json is modified in the working tree. Needs investigation: either a Node version mismatch (restore it) or a legitimate update (commit it). Either way it shouldn't sit unstaged.
  • LOW Three worktree-* branches on the remote look like accidental pushes of local worktree checkouts. Audit and delete if they contain nothing meaningful.
  • LOW V1.0 uses uppercase V — minor inconsistency with semver convention. Only relevant if you add more tags.
  • LOW No pre-commit hooks. CI catches issues, but a light pre-commit step (ESLint + format check) would catch them earlier. Optional.
  • INFO AGENTS.md is untracked. It's a project-convention file in the repo root — worth committing, not ignoring.
  • INFO Repo is lean. 1.4 MB pack, 17.8 KB largest blob, 0 garbage. No large-file problem, no binary bloat. Excellent.
  • INFO Commit messages are strong. Recent commits use scoped conventional-commit prefixes with descriptive bodies. This is genuinely good discipline and worth preserving.
